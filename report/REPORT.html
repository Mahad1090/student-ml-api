Core principle. Git manages the evolution of source code. Pull Requests control how changes enter main. CI verifies those changes. Docker converts approved source code into a reproducible artifact. The container registry stores and distributes versioned artifacts that can later be delivered consistently to staging and production.

3. Application & Automated Tests (Parts 1–2)

The service is a FastAPI application (app.py). The prediction "model" simply doubles the input — the exercise targets the MLOps workflow, not model quality.

The application version is read from the VERSION file at runtime, so it is never hard-coded in code. Pydantic StrictInt | StrictFloat validation makes a non-numeric value return HTTP 422 rather than being silently coerced.

5. GitHub Actions CI (Part 5)

.github/workflows/ci.yml runs on pull_request → main and on pushes to feature branches. It publishes no artifact.

job: test           → checkout → setup-python 3.12 → pip install -r requirements.txt → pytest -q
job: docker-build   → needs: test → checkout → docker build (validation only, no push)

Because docker-build declares needs: test, a failing pytest short-circuits the pipeline (the build job is skipped) and the whole run is FAILED. A failing docker build likewise fails the run. Branch protection then makes that a hard merge gate.

8. Merge Strategy (Part 8)

Squash and merge was used for every PR.

  • Each feature branch carries several iterative WIP commits (PR #1 even contains the deliberate break + fix). Squashing lands one atomic, reviewed change per feature on main.
  • main stays linear and every commit is independently buildable, keeping git bisect meaningful.
  • The squash commit references the PR number ((#1), (#2)) — main → PR is one hop — while the full commit-by-commit history remains on the PR.

9. Dockerization (Part 9)

FROM python:3.12-slim                 # pinned — never python:latest
ARG APP_VERSION / GIT_COMMIT / BUILD_DATE
LABEL org.opencontainers.image.*     # OCI metadata (Part 23)
WORKDIR /app
COPY requirements.txt .              # deps copied first …
RUN pip install --no-cache-dir -r requirements.txt   # … so this layer caches
COPY app.py VERSION ./              # app code last
EXPOSE 5000
CMD ["uvicorn","app:app","--host","0.0.0.0","--port","5000"]

.dockerignore excludes .git, .github, __pycache__, *.pyc, .venv, .env, tests, *.md, the assignment PDF, etc. Good practices demonstrated: explicit base-image version, WORKDIR, dependency-before-code COPY ordering, --no-cache-dir, EXPOSE, and an exec-form CMD that binds 0.0.0.0 (not 127.0.0.1) so the port is reachable from the host.

12. Git Tags & Release Workflow (Parts 13–15)

After each merge: git checkout main && git pull && git tag vX.Y.Z && git push origin vX.Y.Z. Tags present: v1.0.0 → fa0394b, v1.1.0 → 02dc3db.

.github/workflows/release.yml runs only on push: tags: ["v*.*.*"] and performs:

checkout → derive version from tag → run pytest → GHCR login (GITHUB_TOKEN)
        → docker buildx build → tag  X.Y.Z / latest / <short-sha>  → push

The version is derived automatically — version=${GITHUB_REF_NAME#v} turns v1.1.0 into 1.1.0. Nothing is hard-coded; no password is stored in YAML (the GitHub-managed GITHUB_TOKEN with packages: write is used).

15. Rollback Exercise (Part 20)

Assume 1.1.0 has a production issue. Restore 1.0.0 with no source change and no rebuild:

docker rm -f student-ml-api
docker run -d --name student-ml-api -p 5005:5000 ghcr.io/mahad1090/student-ml-api:1.0.0
curl localhost:5005/health   →  {"status":"healthy","application":"student-ml-api","version":"1.0.0"}

Why this beats git clone → pip install → python app.py: the 1.0.0 image is the exact bytes that were tested and previously ran — same OS packages, same pinned Python, same wheels. A fresh pip install can resolve different transitive versions and reintroduce bugs. Rollback is one docker run (seconds, no build toolchain on the host) and is auditable by digest.

17. CI vs Release, Metadata, Commit Tag, Cache (Parts 22–25)

CI workflow vs Release workflow (Part 22)

CI — ci.ymlRelease — release.yml
Triggerpull_request → main, feature-branch pushpush tag v*.*.*
Doestest, validate, build-checktest, build, version, publish
Publishes artifactNoYes

Why not publish an image from every PR? A PR is unreviewed and possibly unstable (or from a fork); publishing pollutes the registry with throwaway tags and risks deploying an un-merged change. Registry storage/bandwidth cost money and most PR builds are never used. Publishing should be a deliberate, tagged, auditable event — and a push credential is far more dangerous in a PR-triggered job than in a tag-triggered one only maintainers can fire.

Image metadata (Part 23)

org.opencontainers.image.title     = student-ml-api
org.opencontainers.image.version   = 1.1.0
org.opencontainers.image.revision  = 02dc3db8bf199a185b6f0c9d0c454fb599e25e12
org.opencontainers.image.source    = https://github.com/Mahad1090/student-ml-api
org.opencontainers.image.created   = <build timestamp>

Verified with docker inspect --format '{{json .Config.Labels}}' (Fig 15).

Commit-SHA tag (Part 24)

Alongside 1.1.0 and latest, the release publishes student-ml-api:02dc3db. Benefit: a semantic tag is a human label that could be re-pushed and latest moves constantly; a commit-SHA tag is 1:1 with an immutable point in source history — given a running container you can name the exact commit, and given a commit you can pull exactly that image.

Build cache (Part 25)

With COPY requirements.txt → RUN pip install → COPY app.py: editing only app.py reuses the cached dependency layer (---> Using cache) and rebuilds in seconds; editing requirements.txt invalidates that layer and everything after it, so pip install re-runs. COPY . . before pip install is worse because any one-character source change forces a full re-install on every build — wasting CI minutes on every commit.

Failure 2 — Missing dependency (deliberately reproduced)

SymptomOn branch chore/failure-demo, CI Unit tests failed during collection; Docker build validation skipped.
Root causehttpx removed from requirements.txt. FastAPI's TestClient wraps httpx, so every test fails to import even though app.py still runs.
EvidenceRun 34498295688: ModuleNotFoundError: No module named 'httpx' / RuntimeError: The starlette.testclient module requires the httpx package (Fig 25).
CorrectionRestored httpx==0.28.1; branch discarded (never merged). A runtime-only missing dep (e.g. dropping uvicorn) would instead pass pytest but fail the container's CMD at start — which is why CI also builds the image.

Failure 3 — Wrong / already-allocated container port (observed locally)

Symptomdocker run -p 5000:5000 → Bind for 0.0.0.0:5000 failed: port is already allocated. curl localhost:5000/health returned a different app's JSON.
Root causeThree containers from an unrelated exercise already published host ports 5000–5002; the new container could not bind and the port that answered belonged to another service.
Evidencedocker ps showed 0.0.0.0:5000->5000/tcp on competent_rhodes, …5001 / …5002 on staging-a/-b; our container stuck in Created.
CorrectionPublished on a free host port: -p 5005:5000. curl localhost:5005/health then returned the correct student-ml-api payload. The container port (EXPOSE 5000, --port 5000) is fixed by the image; only the host side of -p host:container collided.

Related — binding to 127.0.0.1: if the app bound 127.0.0.1 instead of 0.0.0.0, it would only accept connections from inside the container's namespace, so -p 5005:5000 forwarding from the host would get connection reset. This is why the CMD uses --host 0.0.0.0.

19. Viva Questions

  1. Why avoid pushing directly to main? No review, no CI gate, no audit trail — a bad commit is instantly "production". PRs make every change reviewed, tested and revertible as a unit.
  2. Purpose of a PR beyond merging? Code review, discussion, a CI checkpoint, a documented rationale, and a durable link between a change and why it was made.
  3. Why CI before merge? To keep main always green. A failure caught after merge means everyone pulls broken code and the fix needs its own PR.
  4. Image vs container? An image is an immutable, layered filesystem + metadata (a build artifact). A container is a running/stopped instance of an image with its own writable layer, PID, network and lifecycle.
  5. Why version images? So a deploy names an exact artifact, rollbacks are possible, and "what is running?" has a precise answer.
  6. Why is latest insufficient? It is a moving pointer — different bytes over time, recorded nowhere; two machines pulling it a day apart can run different code.
  7. Why promote the same artifact instead of rebuilding? A rebuild can pull different transitive dependencies / base-image patches and produce an untested image. Promotion ships the tested bits.
  8. Purpose of a container registry? A versioned, access-controlled store that distributes immutable image artifacts (by tag and by digest) to any environment.
  9. CI vs release workflow? CI validates proposed changes on PRs and publishes nothing. Release runs on a version tag and is the only thing that builds and pushes a published image.
  10. Why secrets for registry credentials? Hard-coded credentials live in git history forever, are visible to anyone with read access, and cannot be rotated cleanly. Secrets are injected at runtime, masked in logs, and scoped.
  11. How to identify the commit that produced an image? The <short-sha> image tag, or docker inspect → org.opencontainers.image.revision label.
  12. Why does layer ordering affect CI/CD performance? A changed layer invalidates the cache for itself and everything after it — put slow, rarely-changing steps (dependency install) before fast, frequently-changing ones (app code).
  13. How to roll back 1.1.0 → 1.0.0? docker run ghcr.io/mahad1090/student-ml-api:1.0.0 — the old image is still in the registry; no code change, no rebuild.
  14. Git tag vs Docker image tag? The Git tag (v1.1.0) marks a commit in source history and triggers the release; the Docker tag (1.1.0) labels the resulting image in the registry. The workflow derives the second from the first.
  15. App version vs model version changing independently? Both must be recorded per release (here via application_version + model_version) — the same code with a different model, or the same model behind different code, are different systems. It also multiplies the test matrix and complicates rollback (roll back code, model, or both?).
